\sectionBadge{Contexto del Problema \& Arquitectura Multi-Tier}

\subsection{Descripción del Desafío de Ingeniería DevOps}
La organización \textbf{Icesi Tech Solutions} requiere modernizar su plataforma de inventario de productos compuesta por dos componentes desacoplados:
\begin{enumerate}[leftmargin=*,itemsep=1.5pt,topsep=1.5pt]
  \item \textbf{Backend REST (\texttt{product-api}):} Microservicio en \textbf{Spring Boot 3 (Java 17)} con JPA y base de datos H2 en memoria, encargado de exponer operaciones CRUD de productos (\texttt{GET, POST, PUT, DELETE /api/products}).
  \item \textbf{Frontend SPA (\texttt{product-frontend}):} Interfaz de usuario en \textbf{React 18 + Vite + TypeScript} que consume el API a través de la variable de entorno \texttt{VITE\_API\_URL}.
\end{enumerate}

Actualmente el equipo no posee automatización: las pruebas, compilaciones y despliegues se ejecutan manualmente. El objetivo de este taller es estructurar el ciclo completo de entrega continua implementando \textbf{Multi-Stage Dockerfiles}, orquestación con \textbf{Docker Compose} y un pipeline declarativo de 4 jobs en \textbf{GitHub Actions}.

\vspace{0.08cm}
\noindent
\small
\begin{tabularx}{\textwidth}{|L{2.8cm}|X|L{3.5cm}|}
\hline
\rowcolor{icesiLight}
\textbf{Componente} & \textbf{Tecnología \& Stack} & \textbf{Puerto / Endpoint} \\ \hline
\textbf{Backend REST} & Java 17, Spring Boot 3.2, Spring Data JPA, H2 & Puerto \texttt{8080} (\texttt{/api/products}) \\ \hline
\textbf{Frontend SPA} & React 18, TypeScript, Vite 5, Nginx Alpine & Puerto \texttt{3000} (Proxy: \texttt{/}) \\ \hline
\textbf{Orquestación} & Docker Compose v2 (Red Bridge \texttt{product-network}) & \texttt{docker compose up -d} \\ \hline
\textbf{CI/CD Pipeline} & GitHub Actions (\texttt{.github/workflows/ci-cd.yml}) & 4 Jobs (Test, Lint, Build, Smoke) \\ \hline
\end{tabularx}

\sectionBadge{Procedimiento Experimental \& Tareas a Desarrollar}

\subsection{Fase 1: Pruebas Unitarias y Compilación de Artefactos (30 min)}
En el código base suministrado en \texttt{codigo\_base/}:
\begin{enumerate}[leftmargin=*,label=\textbf{\alph*)},itemsep=2pt,topsep=2pt]
  \item En \texttt{backend/}, ejecute la suite de pruebas unitarias y de controlador con Maven:
  \begin{lstlisting}[style=bashstyle]
cd backend && mvn clean test
  \end{lstlisting}
  Verifique que \texttt{ProductServiceTest} y \texttt{ProductControllerTest} reporten 100\% de éxito.
  \item En \texttt{frontend/}, valide la consistencia de tipos TypeScript y genere el build de producción:
  \begin{lstlisting}[style=bashstyle]
cd frontend && npm install && npm run lint && npm run build
  \end{lstlisting}
\end{enumerate}

\subsection{Fase 2: Contenerización Multi-Stage con Docker (30 min)}
Diseñe y optimice los archivos \texttt{Dockerfile} aplicando buenas prácticas de reducción de peso y seguridad:
\begin{itemize}[leftmargin=*,itemsep=2.5pt,topsep=2pt]
  \item \textbf{Backend (\texttt{backend/Dockerfile}):}
    \begin{itemize}[itemsep=1pt]
      \item \textit{Stage 1 (Builder):} \texttt{maven:3.9.6-alpine}. Descarga de dependencias en caché y compilación (\texttt{mvn package -DskipTests}).
      \item \textit{Stage 2 (Runtime):} \texttt{eclipse-temurin:17-jre-alpine}. Copia del archivo \texttt{.jar}, usuario no root (\texttt{appuser}) y puerto \texttt{8080}.
    \end{itemize}
  \item \textbf{Frontend (\texttt{frontend/Dockerfile}):}
    \begin{itemize}[itemsep=1pt]
      \item \textit{Stage 1 (Builder):} \texttt{node:20-alpine}. Instalación limpia (\texttt{npm install}) y generación de estáticos (\texttt{npm run build}).
      \item \textit{Stage 2 (Runtime):} \texttt{nginx:alpine}. Copia de estáticos \texttt{dist/} hacia Nginx con soporte de fallback SPA en \texttt{nginx.conf}.
    \end{itemize}
\end{itemize}

\subsection{Fase 3: Orquestación Multicontenedor con Docker Compose (20 min)}
Complete el archivo \texttt{docker-compose.yml} para orquestar la ejecución conjunta de los servicios:
\begin{enumerate}[leftmargin=*,label=\textbf{\alph*)},itemsep=2pt,topsep=2pt]
  \item Declare una red compartida tipo puente (\texttt{product-network}).
  \item Configure el \textit{healthcheck} en el backend validando la respuesta HTTP en \texttt{http://localhost:8080/api/products}.
  \item Configure la directiva \texttt{depends\_on} con \texttt{condition: service\_healthy} en el contenedor frontend.
  \item Levante el entorno completo y compruebe su funcionamiento en el navegador (\texttt{http://localhost:3000}):
  \begin{lstlisting}[style=bashstyle]
docker compose up -d --build
docker compose ps
curl -i http://localhost:8080/api/products
  \end{lstlisting}
\end{enumerate}

\subsection{Fase 4: Pipeline Declarativo en GitHub Actions (30 min)}
Configure el flujo de automatización en \texttt{.github/workflows/ci-cd.yml} estructurado en 4 etapas:
\begin{enumerate}[leftmargin=*,label=\textbf{\alph*)},itemsep=2.5pt,topsep=2pt]
  \item \textbf{Job 1 (\texttt{test-backend}):} Setup JDK 17 (Temurin), ejecución de \texttt{mvn test} y carga del artefacto JAR (\texttt{upload-artifact}).
  \item \textbf{Job 2 (\texttt{test-frontend}):} Setup Node 20, verificación estática (\texttt{npm run lint}) y compilación del bundle.
  \item \textbf{Job 3 (\texttt{build-docker}):} Construcción de imágenes Docker utilizando \texttt{docker/build-push-action} con tags versionados.
  \item \textbf{Job 4 (\texttt{smoke-test}):} Despliegue con \texttt{docker compose up -d} y validación de disponibilidad mediante consultas \texttt{curl} automatizadas.
\end{enumerate}

\sectionBadge{Cuestionario de Análisis \& Conceptos DevOps (10 min)}

Responda brevemente a las siguientes preguntas con base en la experiencia de laboratorio:
\begin{enumerate}[leftmargin=*,label=\textbf{\arabic*.},itemsep=4pt,topsep=3pt]
  \item \textbf{Inmutabilidad y Multi-Stage:} ¿Por qué no se debe incluir el SDK completo de Java (JDK) ni el compilador Maven en la imagen Docker final de producción? ¿Qué impacto tiene esta decisión en el tamaño de la imagen y en la superficie de ataque (\textit{CVEs})?
  \item \textbf{Shift-Left Testing en CI:} Explique qué sucede si un desarrollador introduce un cambio que rompe una prueba unitaria en el Backend. ¿Cómo protege el pipeline de GitHub Actions la estabilidad de la rama \texttt{main}?
  \item \textbf{Pruebas de Humo (Smoke Testing):} ¿Cuál es la diferencia fundamental entre una prueba unitaria (\textit{Unit Test}) ejecutada en la fase de build y una prueba de humo (\textit{Smoke Test}) ejecutada tras levantar los contenedores?
\end{enumerate}
